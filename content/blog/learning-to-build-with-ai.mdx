## Start with the problem

AI tools can make it tempting to ask for a solution before the problem is clear. I try to begin by describing what the software should do, what constraints matter, and how I will know the result is correct. A clear request makes the response easier to evaluate.

That first step also keeps me engaged in the work. The tool can suggest a starting point, but I still need to understand the goal, the existing code, and the people who will use the result.

## Use suggestions as a draft

Generated code is most helpful when I treat it as a draft. I read through the change, compare it with the patterns already in the project, and check whether the solution handles the important cases. If something feels unfamiliar, I pause to learn what it does before keeping it.

This approach takes more care than pasting a response directly into a codebase, but it prevents a different kind of delay: debugging a feature whose assumptions I never examined. Understanding the code is part of the deliverable.

## Keep responsibility with the builder

AI can help explore alternatives, write repetitive scaffolding, or explain an error message. It cannot decide whether the behavior is appropriate for the product or whether a tradeoff is worth making. Those decisions still need context and judgment.

I want these tools to make me more thoughtful, not less involved. The best workflow gives me a faster way to compare ideas while keeping the final review, testing, and responsibility where they belong: with the people building the software.
